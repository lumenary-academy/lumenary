<Section id="motivation" kind="motivation" title="Two correct programs">

A national examinations board has a million candidate records and must check that no two candidates were given the same ID. Here are two correct ways to do it in Python:

```python
def has_duplicate_pairs(ids):
    n = len(ids)
    for i in range(n):
        for j in range(i + 1, n):
            if ids[i] == ids[j]:
                return True
    return False

def has_duplicate_set(ids):
    seen = set()
    for x in ids:
        if x in seen:
            return True
        seen.add(x)
    return False
```

Both are always right. But when there are no duplicates, the first compares every pair: $n(n-1)/2$ comparisons, about $5 \times 10^{11}$ for $n = 10^6$. Even at a hundred million comparisons a second that is well over an hour, and Python is slower. The second does one set lookup and one insertion per record and finishes in well under a second.

Correctness is not enough: an answer that arrives next week is, for most purposes, no answer. This lesson gives you the tools to predict a program's cost **before** running it, to compare algorithms independently of the machine, and to check predictions by experiment. Every later lesson uses them.

</Section>

<Section id="intuition" kind="intuition" title="Count steps, not seconds">

Why not just time programs? Because seconds depend on the processor, the language, the Python version and what else the computer is doing, so a measurement on one laptop says little about a phone or a server.

Instead, we count **steps**: simple operations such as an arithmetic operation, a comparison, an assignment, reading `xs[i]`, or calling a function. Each takes at most some fixed amount of time on a given machine, so if we know how the *number* of steps grows with the input, we know how the time grows, up to a constant factor that depends on the machine. This idealised machine, in which every simple operation costs one unit, is called the **cost model** (formally, a *random-access machine*, or RAM).

<Narrator who="gideon">

"Every arithmetic operation costs one unit" quietly assumes the numbers fit in a machine word, typically 64 bits. Python's integers have no such limit, and adding two numbers with a million digits each takes time proportional to a million, not one step. When the numbers themselves grow with the input, as in exact factorials or other big-number arithmetic, the cost of each operation has to be counted too.

</Narrator>

We then make two simplifications, both deliberate:

1. **We describe cost as a function of the input size $n$**: the length of a list, the number of records, the number of digits.
2. **We care about growth, not constants.** The difference between $3n$ and $5n$ steps can be erased by a faster machine or a better compiler; the difference between $n$ and $n^2$ cannot, once $n$ is large.

<Analogy>

To compare walking with driving for a long journey, you don't care that the driver spends a minute finding the car keys. What matters is how the journey time *grows* with distance: one hour per 5 km versus one hour per 80 km. The key-finding is a constant; the speed is the growth rate. Asymptotic analysis is the habit of ignoring the keys.

</Analogy>

</Section>

<Section id="definitions" kind="definitions" title="Running time and the three notations">

<Definition term="running time">

For an algorithm $A$, let $T_A(x)$ be the number of steps $A$ takes on input $x$. Its **worst-case running time** is $T(n) = \max \{ T_A(x) : x \text{ has size } n \}$, and its **best-case running time** is the corresponding minimum. Its **average-case running time** is the expected value of $T_A(x)$ when inputs of size $n$ are drawn from a stated probability distribution.

</Definition>

Running times are functions from input sizes to step counts. To compare such functions while ignoring constant factors and small inputs, we use three notations. Throughout, $f$ and $g$ are functions from the natural numbers to the non-negative reals.

<Definition term="O, Ω and Θ">

- $f(n) = O(g(n))$ ("$f$ is big-O of $g$") if there are constants $c > 0$ and $n_0$ such that $f(n) \le c\, g(n)$ for all $n \ge n_0$. It says $f$ grows **at most** as fast as $g$.
- $f(n) = \Omega(g(n))$ ("big-Omega") if there are constants $c > 0$ and $n_0$ such that $f(n) \ge c\, g(n)$ for all $n \ge n_0$. It says $f$ grows **at least** as fast as $g$.
- $f(n) = \Theta(g(n))$ ("big-Theta") if both hold: $f(n) = O(g(n))$ and $f(n) = \Omega(g(n))$. It says $f$ and $g$ grow **at the same rate**, up to constant factors.

</Definition>

The "=" here is a traditional abuse of notation: $O(g)$ is really a **set** of functions, and $f = O(g)$ means $f \in O(g)$. That is why we never write $O(g) = f$, and why $n = O(n^2)$ and $n^2 = O(n^2)$ do not imply $n = n^2$.

Two more pieces of vocabulary are useful. We write $f(n) = o(g(n))$ ("little-o") when $f(n)/g(n) \to 0$: $f$ grows **strictly slower** than $g$. And the definitions give a handy test:

<Theorem name="The limit test">

Suppose $\lim_{n \to \infty} f(n)/g(n) = L$ exists (possibly $\infty$). If $0 < L < \infty$, then $f = \Theta(g)$. If $L = 0$, then $f = O(g)$ but $f \ne \Omega(g)$. If $L = \infty$, then $f = \Omega(g)$ but $f \ne O(g)$.

</Theorem>

<Proof>

If $0 < L < \infty$, then by the definition of a limit there is an $n_0$ with $L/2 \le f(n)/g(n) \le 2L$ for all $n \ge n_0$, so $c = 2L$ witnesses $O$ and $c = L/2$ witnesses $\Omega$. If $L = 0$, then $f(n)/g(n) \le 1$ for large $n$, giving $O$ with $c = 1$; and for any proposed $c > 0$, eventually $f(n)/g(n) < c$, so no $c$ can witness $\Omega$. The case $L = \infty$ is symmetric.

</Proof>

<Narrator who="gideon">

The test is sufficient, not necessary: it needs the limit to exist. Take $f(n) = n\,(2 + \sin n)$. It lies between $n$ and $3n$, so $f = \Theta(n)$ straight from the definition, yet $f(n)/n = 2 + \sin n$ keeps wandering and has no limit. When the test does not apply, go back to exhibiting constants.

</Narrator>

</Section>

<Section id="proving-bounds" kind="examples" title="Proving bounds">

To prove an $O$ or $\Omega$ bound from the definition, you exhibit the constants. Any constants that work will do; there is no need to find the best ones.

<Theorem name="A quadratic">

$3n^2 + 10n + 7 = \Theta(n^2)$.

</Theorem>

<Proof>

Upper bound: for $n \ge 1$ we have $10n \le 10n^2$ and $7 \le 7n^2$, so $3n^2 + 10n + 7 \le 20 n^2$. Take $c = 20$, $n_0 = 1$. Lower bound: for all $n \ge 0$, $3n^2 + 10n + 7 \ge 3n^2$. Take $c = 3$, $n_0 = 0$.

</Proof>

The same argument shows that any polynomial $a_d n^d + \dots + a_1 n + a_0$ with $a_d > 0$ is $\Theta(n^d)$: the leading term dominates, and the lower-order terms only affect the constants. This is why we write $\Theta(n^2)$ and not $\Theta(3n^2 + 10n + 7)$.

<Theorem name="Logarithm bases do not matter">

For any constants $a, b > 1$, $\log_a n = \Theta(\log_b n)$.

</Theorem>

<Proof>

By the change-of-base formula, $\log_a n = \dfrac{\log_b n}{\log_b a}$, and $\log_b a$ is a positive constant. So $\log_a n$ is a constant multiple of $\log_b n$, which is $\Theta$ by definition.

</Proof>

So we simply write $\Theta(\log n)$. (In computer science, an unmarked $\log$ often means $\log_2$, because halving is everywhere; for asymptotics it doesn't matter.)

<Theorem name="Polynomials are beaten by exponentials">

For every fixed $k$, $n^k = o(2^n)$. In particular $2^n \ne O(n^k)$.

</Theorem>

<Proof>

Take logarithms: $\log_2 (n^k / 2^n) = k \log_2 n - n$. Since $\log_2 n / n \to 0$ (see <TopicLink id="math.analysis.exponential-logarithmic-functions">Exponential and logarithmic functions</TopicLink>), we have $k \log_2 n - n = n\,(k \log_2 n / n - 1) \to -\infty$, so $n^k / 2^n \to 0$. By the limit test, $n^k = O(2^n)$ but not $\Omega(2^n)$, which also rules out $2^n = O(n^k)$.

</Proof>

In practice you rarely go back to the definitions, because a few rules cover most cases:

- **Constant factors vanish:** $c \cdot f = \Theta(f)$ for any constant $c > 0$.
- **Sums are dominated by their largest term:** $f + g = \Theta(\max(f, g))$. Doing a $\Theta(n)$ step and then a $\Theta(n^2)$ step costs $\Theta(n^2)$.
- **Products multiply:** a loop that runs $\Theta(f)$ times with a body costing $\Theta(g)$ costs $\Theta(f \cdot g)$, provided the body's cost doesn't vary too much between iterations (if it does, add up the iterations exactly, as below).
- **Transitivity:** if $f = O(g)$ and $g = O(h)$ then $f = O(h)$; the same for $\Omega$ and $\Theta$.

</Section>

Numbers make the differences vivid. Suppose a machine does $10^8$ simple steps per second, a fair order of magnitude for compiled code (Python is typically ten to a hundred times slower per step). Then, roughly:

| Growth | Steps for $n = 10^3$ | Steps for $n = 10^6$ | Largest $n$ in about one second |
| --- | --- | --- | --- |
| $\log_2 n$ | 10 | 20 | astronomically large |
| $n$ | $10^3$ | $10^6$ | $10^8$ |
| $n \log_2 n$ | $10^4$ | $2 \times 10^7$ | about $4 \times 10^6$ |
| $n^2$ | $10^6$ | $10^{12}$ | $10^4$ |
| $n^3$ | $10^9$ | $10^{18}$ | about 460 |
| $2^n$ | about $10^{301}$ | (hopeless) | about 26 |

Look at the last column from the other side. If you buy a computer 100 times faster, a linear algorithm handles inputs 100 times bigger, a quadratic one only 10 times bigger, and an exponential one only about 7 more items, since $2^7 \approx 100$. **Better hardware helps good algorithms most.** The divide between polynomial growth ($n^k$) and exponential growth is the starting point of complexity theory, which asks which problems have polynomial-time algorithms at all; see <TopicLink id="math.comp.complexity-theory">Computational complexity</TopicLink> in Lumenary Math and <LessonLink slug="hard-problems">Hard problems</LessonLink> later in this course.

<Section id="counting" kind="examples" title="Counting steps in code">

Most running-time analysis comes down to a few loop patterns. In each, count how many times the innermost statement runs, as an exact sum where you can, then simplify.

**One loop over the data.** `for x in xs:` with a constant-cost body runs $n$ times: $\Theta(n)$.

**Two independent nested loops.** `for i in range(n): for j in range(n):` runs the inner body $n \cdot n$ times: $\Theta(n^2)$.

**A triangular loop.** When the inner loop starts after the outer index, as in `has_duplicate_pairs`, the inner body runs $(n-1) + (n-2) + \dots + 1 + 0$ times:

$$
\sum_{i=0}^{n-1} (n - 1 - i) = \sum_{k=0}^{n-1} k = \frac{n(n-1)}{2} = \Theta(n^2).
$$

Half the work of the full square, but the same growth rate: constants don't change the class.

**A halving loop.** `while n > 1: n = n // 2` runs $\lfloor \log_2 n \rfloor$ times, because after $k$ iterations $n$ has been divided by about $2^k$, and the loop stops once $2^k$ exceeds $n$. So $\Theta(\log n)$. Doubling loops (`j = 1; while j < n: j *= 2`) are logarithmic for the same reason.

<Narrator who="chloe">

There is an exact way to see that count: `n // 2` deletes the last binary digit of $n$, so the loop runs once for every digit after the first, and $\lfloor \log_2 n \rfloor$ is `n.bit_length() - 1`. For $n = 1000$, binary `1111101000`, that is $9$, the number in the program's "halving" column.

</Narrator>

**A loop inside a halving loop, or the reverse.** `for i in range(n):` around a doubling `while` loop costs $n \cdot \Theta(\log n) = \Theta(n \log n)$.

The program below counts the steps of each pattern and compares them with the formulas.

```python run
import math

def steps_square(n):
    steps = 0
    for i in range(n):
        for j in range(n):
            steps += 1
    return steps

def steps_triangle(n):
    steps = 0
    for i in range(n):
        for j in range(i + 1, n):
            steps += 1
    return steps

def steps_halving(n):
    steps = 0
    while n > 1:
        n = n // 2
        steps += 1
    return steps

def steps_n_log_n(n):
    steps = 0
    for i in range(n):
        j = 1
        while j < n:
            j *= 2
            steps += 1
    return steps

print(f"{'n':>5} {'square':>8} {'triangle':>9} {'n(n-1)/2':>9} {'halving':>8} {'floor(log2 n)':>14} {'n log':>7}")
for n in [8, 100, 1000]:
    print(f"{n:>5} {steps_square(n):>8} {steps_triangle(n):>9} {n * (n - 1) // 2:>9}"
          f" {steps_halving(n):>8} {math.floor(math.log2(n)):>14} {steps_n_log_n(n):>7}")
```

### Hidden loops

A single line of Python can hide a loop, and the analysis must count it. Typical costs in CPython, the standard Python implementation:

| Operation | Cost |
| --- | --- |
| `xs[i]`, `xs[i] = v`, `len(xs)` | $\Theta(1)$ |
| `xs.append(v)`, `xs.pop()` | $\Theta(1)$ amortised (see below) |
| `xs.insert(0, v)`, `xs.pop(0)` | $\Theta(n)$: every item shifts along |
| `v in xs`, `xs.index(v)`, `xs.count(v)` | $\Theta(n)$: a search through the list |
| `xs[a:b]`, `xs.copy()` | $\Theta(b - a)$, $\Theta(n)$: a copy is made |
| `v in s`, `s.add(v)` for a set; `d[k]` for a dict | $\Theta(1)$ on average |
| `sorted(xs)`, `xs.sort()` | $\Theta(n \log n)$ worst case |

So a loop that does `if v in xs:` on a list inside a `for` over $n$ items is quadratic, even though it looks like a single loop. That one hidden cost is the entire difference between the two duplicate checkers at the start of the lesson.

</Section>

<Section id="cases" kind="human" title="Best, worst and average case">

Consider **linear search**: look through a list from the front until you find a target $t$.

- **Best case:** $t$ is first. One comparison: $\Theta(1)$.
- **Worst case:** $t$ is last or absent. $n$ comparisons: $\Theta(n)$.
- **Average case:** if $t$ is present and equally likely to be at each of the $n$ positions, the expected number of comparisons is $\frac{1}{n}(1 + 2 + \dots + n) = \frac{n+1}{2}$, which is $\Theta(n)$.

Notice that there are two *independent* choices here. The **case** (best, worst, average) chooses *which function* we are describing. The **notation** ($O$, $\Omega$, $\Theta$) chooses *what kind of bound* we state about that function. "The worst-case running time of linear search is $\Theta(n)$" and "its best-case running time is $\Theta(1)$" are both precise, true statements. "Linear search is $O(n)$" is also true, since every case is at most linear, but it is a weaker statement.

Engineers usually quote the **worst case**, because it is a guarantee that no input, however unlucky or malicious, does worse. Average-case statements are only as good as their assumption about the inputs, which real data (already sorted, or crafted by an attacker) often breaks. The **amortised** cost, next, is a worst-case guarantee about *sequences* of operations.

</Section>

<Section id="amortised" kind="examples" title="Amortised cost: why append is cheap">

A Python list stores references to its items in one contiguous block of memory, so that `xs[i]` can be found by arithmetic in one step. But then what happens when you `append` to a list whose block is full? A new, bigger block must be allocated and every existing reference copied across. That single append costs $\Theta(n)$. If that happened on every append, building a list of $n$ items would cost $\Theta(n^2)$.

The trick, used by Python's lists, Java's `ArrayList`, C++'s `std::vector` and many others, is to **over-allocate**: when the block is full, grow its capacity by a constant *factor*, not by a constant amount. Then expensive appends become rarer and rarer as the list grows.

<Definition term="amortised cost">

An operation has **amortised cost** $a$ if, starting from an empty structure, every sequence of $m$ such operations costs at most $m \cdot a$ in total, in the worst case. Individual operations may be expensive, as long as they are rare enough to be paid for by the cheap ones.

</Definition>

<Theorem name="Doubling gives constant amortised appends">

If a dynamic array starts with capacity 1 and doubles its capacity whenever an append finds it full, then any sequence of $n$ appends performs fewer than $2n$ copies in total, so each append costs $O(1)$ amortised.

</Theorem>

<Proof>

Copies happen only when the array is full, that is, when its size is a power of two: at sizes $1, 2, 4, \dots, 2^k$ where $2^k < n$. The total number of items copied is
$$
1 + 2 + 4 + \dots + 2^k = 2^{k+1} - 1 < 2 \cdot 2^k < 2n.
$$
Adding the $n$ writes of the new items themselves, the whole sequence costs fewer than $3n$ steps, which is $O(1)$ per append.

</Proof>

The same argument works for any growth factor $r > 1$: the copy sizes form a geometric series summing to at most about $\frac{r}{r-1} \cdot n$. CPython uses a gentle factor of about $1.125$ plus a small constant (see `listobject.c` in the references), trading more copies for less wasted memory. Growing by a fixed amount instead, say 100 slots at a time, breaks the guarantee: copy sizes $100, 200, 300, \dots$ add up to $\Theta(n^2)$.

```python run
import sys

# Watch a real list's memory jump only now and then as it grows
xs = []
last = sys.getsizeof(xs)
changes = []
for i in range(1, 129):
    xs.append(i)
    size = sys.getsizeof(xs)
    if size != last:
        changes.append(i)
        last = size
print("The list's block grew when its length reached:", changes)

# Count copies for two growth strategies
def copies_needed(n, grow):
    capacity, size, copies = 1, 0, 0
    for _ in range(n):
        if size == capacity:
            copies += size              # move every item to the new block
            capacity = grow(capacity)
        size += 1
    return copies

def double(c):
    return 2 * c

def add_100(c):
    return c + 100

for n in [1000, 10_000, 100_000]:
    d = copies_needed(n, double)
    a = copies_needed(n, add_100)
    print(f"n = {n:>7}: doubling {d:>7} copies ({d / n:.2f} per append);"
          f" +100: {a:>10} copies ({a / n:.1f} per append)")
```

The exact sizes depend on the Python version and on whether it runs on a 64-bit machine or (as in the browser) a 32-bit WebAssembly build, but the gaps between growth points widen as the list gets longer. And the copy counts tell the story: with doubling, the cost per append stays below 2 however large $n$ gets; with fixed-size growth, it climbs with $n$. You'll build a dynamic array yourself in <LessonLink slug="lists-stacks-queues">Lists, stacks and queues</LessonLink>.

<Narrator who="margaret">

Read the per-append columns closely. Doubling gives $1.02$, $1.64$ and $1.31$: it wobbles because it depends on how far $n$ is past the last power of two ($10\,000$ is just past $8192$, so a copy of $8192$ items has just happened), but it never reaches 2. The $+100$ column reads $4.5$, $49.5$, $499.5$, growing tenfold when $n$ does: about $n/200$ per append, so $\Theta(n^2)$ in total.

<Section id="experiments" kind="computation" title="Timing experiments">

Analysis predicts; experiment checks. The most useful experiment is the **doubling experiment**: run the program on inputs of size $n$, $2n$, $4n$, … and look at the *ratio* of successive times. If $T(n) \approx c\, n^k$, then
$$
\frac{T(2n)}{T(n)} \approx \frac{c\,(2n)^k}{c\, n^k} = 2^k,
$$
so a ratio near 2 suggests linear growth, near 4 quadratic, near 8 cubic. The unknown constant $c$, which depends on the machine, cancels out. Taking $\log_2$ of the ratio estimates the exponent $k$ directly.

Some care makes timings trustworthy: use `time.perf_counter()` (a high-resolution clock), repeat each measurement and keep the **minimum** (other activity on the machine can only make a run slower, never faster), and use inputs large enough that each run takes at least a few milliseconds. Python's `timeit` module packages these habits.

```python run
import math
import time

def has_duplicate_pairs(ids):
    n = len(ids)
    for i in range(n):
        for j in range(i + 1, n):
            if ids[i] == ids[j]:
                return True
    return False

def has_duplicate_set(ids):
    seen = set()
    for x in ids:
        if x in seen:
            return True
        seen.add(x)
    return False

def best_time(f, data, repeats=3):
    best = float("inf")
    for _ in range(repeats):
        start = time.perf_counter()
        f(data)
        best = min(best, time.perf_counter() - start)
    return best

def doubling(f, sizes):
    previous = None
    for n in sizes:
        t = best_time(f, list(range(n)))     # distinct items: the worst case
        if previous is None:
            print(f"  n = {n:>7}: {t * 1000:8.2f} ms")
        else:
            ratio = t / previous
            print(f"  n = {n:>7}: {t * 1000:8.2f} ms   ratio {ratio:4.1f}   exponent about {math.log2(ratio):.1f}")
        previous = t

print("all pairs:")
doubling(has_duplicate_pairs, [400, 800, 1600])
print("with a set:")
doubling(has_duplicate_set, [50_000, 100_000, 200_000])
```

Your times will differ from anyone else's, but the ratios should come out near 4 for the pairs version and near 2 for the set version, as the analysis predicts. If a measured ratio disagrees with your analysis, one of them is wrong, and finding out which is always instructive. (For tiny $n$, fixed overheads dominate and ratios drift towards 1.)

Memory can be analysed the same way. `has_duplicate_set` uses $\Theta(n)$ extra memory for its set, while `has_duplicate_pairs` uses $\Theta(1)$. Spending memory to save time is one of the most common trades in computing.

</Section>

<Section id="misconceptions" kind="misconceptions" title="Common misconceptions">

<Misconception>

**"$O(n)$ means it takes $n$ steps."** It means *at most a constant times* $n$, for large enough $n$. An algorithm taking $1000n + 10^6$ steps is $O(n)$, and so is one taking $\log n$ steps: $O$ is only an upper bound.

</Misconception>

<Misconception>

**"Big-O means worst case; big-Ω means best case."** The case and the notation are independent choices. You can give an $O$ bound on the best case or an $\Omega$ bound on the worst case. "Comparison sorting needs $\Omega(n \log n)$ comparisons in the worst case" is a famous lower bound on a worst case, which you'll meet in <LessonLink slug="searching-and-sorting">Searching and sorting</LessonLink>.

</Misconception>

<Misconception>

**"Constants never matter."** They don't affect the growth class, but they matter enormously in practice. For small inputs a $\Theta(n^2)$ algorithm with a tiny constant can beat a $\Theta(n \log n)$ one with a large constant, which is why Python's own sort switches to insertion sort for short stretches of data. Memory access patterns can also change real speed by large factors, as <LessonLink slug="memory-hierarchy">The memory hierarchy</LessonLink> explains.

</Misconception>

<Misconception>

**"Computers are so fast now that efficiency doesn't matter."** Unless the algorithm is linear or better, a faster machine multiplies the solvable problem size by much less than its speed-up, and data keeps growing too.

</Misconception>

</Section>

<Section id="history" kind="history" title="Where the notation came from">

The symbol $O$ was introduced by the number theorist Paul Bachmann in 1894 and popularised by Edmund Landau, which is why these are still called *Landau symbols*; they described the error in approximations, such as counting primes. In 1965 Juris Hartmanis and Richard Stearns measured problems by the time a machine needs as a function of input length, founding complexity theory (Turing Award, 1993), and in the same year Alan Cobham and Jack Edmonds independently proposed "polynomial time" as the mathematical stand-in for "efficient". In 1976 Donald Knuth, whose *The Art of Computer Programming* helped make the analysis of algorithms a discipline, wrote a short letter fixing the meanings of $\Omega$ and $\Theta$ used here; before that, authors used $\Omega$ in different senses.

</Section>
