<Section id="motivation" kind="motivation" title="From here to there">

An ambulance dispatcher in São Paulo needs the fastest route from the nearest station to a caller, with travel times that change through the day. Inside the internet, routers running the OSPF protocol each compute the shortest paths from themselves to every other router in their network, and recompute them within seconds when a link fails. A currency trader asks whether converting rupees to yen to euros and back to rupees could ever end with more rupees than she started with. A game engine moves a hundred characters across a map every frame without any of them walking into a wall.

All of these are **shortest-path problems** on weighted graphs. In <LessonLink slug="graphs">Graphs</LessonLink>, breadth-first search found paths with the fewest *edges*. Now edges have **weights** (kilometres, seconds, money, risk), and we want paths of least total weight. This lesson develops the four classical algorithms, each suited to a different situation:

| Algorithm | Problem | Weights | Time |
| --- | --- | --- | --- |
| Dijkstra | one source to all | non-negative | $O((V + E)\log V)$ with a binary heap |
| Bellman–Ford | one source to all | any; detects negative cycles | $O(VE)$ |
| Floyd–Warshall | all pairs | any; detects negative cycles | $O(V^3)$ |
| A* | one source to one target | non-negative, plus a heuristic | often far less than Dijkstra |

Then we look at how real routing engines answer queries on continental road networks in milliseconds, which needs one more idea: **preprocessing**.

</Section>

<Section id="definitions" kind="definitions" title="Definitions">

<Definition term="path weight and distance">

In a directed graph with edge weights $w(u, v)$, the **weight** of a path is the sum of its edge weights. The **distance** $\delta(s, v)$ is the least weight of any path from $s$ to $v$; it is $\infty$ if there is no path. A **shortest path** is a path achieving it. (Undirected graphs are handled by replacing each edge with two directed ones.)

</Definition>

<Definition term="negative cycle">

A **negative cycle** is a cycle whose total weight is negative. If one can be reached from $s$ and can reach $v$, then going round it again and again makes paths to $v$ arbitrarily light, and $\delta(s, v)$ is undefined (or $-\infty$).

</Definition>

<Definition term="relaxation">

Shortest-path algorithms keep an estimate $d[v]$ for each vertex, initially $d[s] = 0$ and $d[v] = \infty$ otherwise. **Relaxing** an edge $(u, v)$ means: if $d[u] + w(u, v) < d[v]$, set $d[v] = d[u] + w(u, v)$ and $\text{parent}[v] = u$.

</Definition>

</Section>

<Section id="relaxation" kind="human" title="The common core: relaxation">

Three simple facts underlie every algorithm in this lesson.

1. **Subpaths of shortest paths are shortest paths.** If the best route from $s$ to $v$ passes through $u$, its first part is a best route from $s$ to $u$; otherwise we could swap in a better first part and improve the whole. This is the optimal substructure of <LessonLink slug="dynamic-programming">dynamic programming</LessonLink>.
2. **Triangle inequality.** For every edge $(u, v)$: $\delta(s, v) \le \delta(s, u) + w(u, v)$, since one way to reach $v$ is to reach $u$ optimally and then take the edge.
3. **Estimates never undershoot.** Throughout any sequence of relaxations, $d[v] \ge \delta(s, v)$, because $d[v]$ is always either $\infty$ or the weight of an actual path (the one traced by the parent pointers). And once $d[v] = \delta(s, v)$, it never changes again.

So an algorithm is correct if it relaxes the right edges in a good enough order that every $d[v]$ comes down to $\delta(s, v)$. The algorithms differ only in **which** edges they relax and **in what order**: Bellman–Ford relaxes everything repeatedly; Dijkstra relaxes each edge once, in a cleverly chosen order.

</Section>

<Section id="dijkstra" kind="human" title="Dijkstra's algorithm">

Edsger Dijkstra designed his algorithm in 1956, reportedly in about twenty minutes while sitting at a café terrace in Amsterdam with his fiancée, to demonstrate a new computer on a problem anyone could understand (a road map of the Netherlands). The idea is BFS with a **priority queue** in place of the plain queue: always settle the closest vertex not yet settled.

```text
Dijkstra(G, s):
    d[s] = 0, d[v] = infinity for every other v
    put (0, s) in a min-heap
    while the heap is not empty:
        pop (du, u) with the smallest du
        if u is already settled: continue          (a stale entry: lazy deletion)
        settle u
        for each edge (u, v) with weight w:
            if du + w < d[v]: d[v] = du + w, parent[v] = u, push (d[v], v)
```

<Theorem name="Dijkstra is correct for non-negative weights">

If every edge weight is non-negative, then when a vertex $u$ is settled, $d[u] = \delta(s, u)$. Consequently Dijkstra's algorithm computes all distances from $s$, and the parent pointers form a tree of shortest paths. With a binary heap and lazy deletion it runs in $O((V + E) \log V)$ time.

</Theorem>

<Proof>

Suppose not, and let $u$ be the first vertex settled with $d[u] > \delta(s, u)$ (so $u \ne s$, and $u$ is reachable). Take a shortest path from $s$ to $u$, and let $y$ be the first vertex on it that is not yet settled at the moment $u$ is popped; let $x$ be the vertex before $y$ on the path. Then $x$ is settled, and since it was settled before $u$, $d[x] = \delta(s, x)$; when $x$ was settled, the edge $(x, y)$ was relaxed, so

$$d[y] \le \delta(s, x) + w(x, y) = \delta(s, y) \le \delta(s, u) < d[u].$$

The equality uses fact 1 (the path up to $y$ is shortest); the next inequality uses **non-negative weights** (the rest of the path from $y$ to $u$ cannot have negative weight). So $y$ sits in the heap with a smaller key than $u$, and the heap would have popped $y$ before $u$. Contradiction.

Each vertex is settled once, and each edge relaxed once, when its tail is settled. Each relaxation pushes at most one heap entry, so the heap holds at most $E + 1$ entries, and every push and pop costs $O(\log E) = O(\log V)$ (since $E \le V^2$).

</Proof>

**Why negative edges break it.** The proof's key step is that extending a path never makes it lighter. Take edges $s \to a$ of weight 2, $s \to b$ of weight 3, $b \to a$ of weight $-2$ and $a \to c$ of weight 1. Dijkstra settles $a$ at distance 2 and, through it, gives $c$ distance 3; only then does it settle $b$ and find the lighter route to $a$, of weight $3 - 2 = 1$. But $a$ is already settled, so its edges are never relaxed again, and $c$ keeps the wrong distance 3 instead of 2. The error spreads to everything reached from $a$.

```python run
import heapq

def dijkstra(graph, s):
    """graph: dict u -> list of (v, weight), weights >= 0. Returns (dist, parent)."""
    dist, parent, settled = {s: 0}, {s: None}, set()
    heap = [(0, s)]
    while heap:
        du, u = heapq.heappop(heap)
        if u in settled:
            continue                                  # stale entry: u was settled more cheaply
        settled.add(u)
        for v, w in graph.get(u, []):
            if du + w < dist.get(v, float("inf")):
                dist[v], parent[v] = du + w, u
                heapq.heappush(heap, (dist[v], v))
    return dist, parent

def route(parent, v):
    path = []
    while v is not None:
        path.append(v)
        v = parent[v]
    return path[::-1]

# Driving times in minutes between towns on an imaginary map (each road works both ways).
roads = [("Kisima", "Pradera", 25), ("Kisima", "Fjellby", 40), ("Pradera", "Fjellby", 10),
         ("Pradera", "Hanami", 55), ("Fjellby", "Hanami", 30), ("Fjellby", "Oasis", 70),
         ("Hanami", "Oasis", 15), ("Hanami", "Tidewater", 45), ("Oasis", "Tidewater", 20)]
graph = {}
for a, b, minutes in roads:
    graph.setdefault(a, []).append((b, minutes))
    graph.setdefault(b, []).append((a, minutes))

dist, parent = dijkstra(graph, "Kisima")
for town in sorted(dist, key=dist.get):
    print(f"{town:10} {dist[town]:3} min  via {' -> '.join(route(parent, town))}")

tricky = {"s": [("a", 2), ("b", 3)], "b": [("a", -2)], "a": [("c", 1)]}
print("with a negative edge, Dijkstra says d[c] =", dijkstra(tricky, "s")[0]["c"], "but the truth is 2")
```

With a Fibonacci heap the bound improves to $O(E + V \log V)$ (Fredman and Tarjan, 1987), but binary or 4-ary heaps are faster on real road networks. In OSPF ([RFC 2328](https://www.rfc-editor.org/info/rfc2328/)), every router floods the state of its links to the others and then runs Dijkstra on the resulting map of the network.

</Section>

<Section id="bellman-ford" kind="human" title="Bellman–Ford and negative cycles">

When some weights are negative (refunds, energy recovered going downhill, or the logarithms of exchange rates below), we need an algorithm that does not settle vertices early. **Bellman–Ford** (Richard Bellman 1958, Lester Ford 1956, Edward Moore 1959) simply relaxes **every** edge, in any order, $V - 1$ times.

<Theorem name="Bellman–Ford">

After $i$ rounds of relaxing all edges, $d[v]$ is at most the weight of the lightest path from $s$ to $v$ that uses at most $i$ edges. If no negative cycle is reachable from $s$, then after $V - 1$ rounds $d[v] = \delta(s, v)$ for every $v$. A negative cycle is reachable from $s$ if and only if some edge can still be relaxed in a further, $V$-th round. The running time is $O(VE)$.

</Theorem>

<Proof>

The first claim is by induction on $i$: a lightest path with at most $i$ edges ending in the edge $(u, v)$ consists of a path to $u$ with at most $i - 1$ edges (whose weight is $\ge d[u]$ after round $i - 1$ by induction) plus $(u, v)$, and round $i$ relaxes $(u, v)$. Without negative cycles, some shortest path to each vertex is **simple** (repeating a vertex would include a cycle, of non-negative weight, which can be cut out), so it has at most $V - 1$ edges, and after $V - 1$ rounds $d[v] \le \delta(s, v)$; with fact 3, equality.

If no negative cycle is reachable, all $d$ values are final after $V - 1$ rounds, so nothing can be relaxed in round $V$. Conversely, suppose a reachable cycle $v_1 \to \cdots \to v_k \to v_1$ has negative weight but no edge can be relaxed, so $d[v_{j+1}] \le d[v_j] + w(v_j, v_{j+1})$ around the cycle. Adding these $k$ inequalities, the $d$ terms cancel, leaving $0 \le$ the cycle's weight, a contradiction.

</Proof>

Bellman–Ford is dynamic programming in disguise: the state is (vertex, number of edges allowed). It is also naturally **distributed**: each node only needs its neighbours' current estimates. The RIP routing protocol ([RFC 2453](https://www.rfc-editor.org/info/rfc2453/)) is exactly this, with routers periodically telling their neighbours their distance to every destination.

**Currency arbitrage.** If one rupee buys $r_{ab}$ units of currency $b$, a cycle of exchanges multiplies your money by the product of its rates. Give the edge from $a$ to $b$ the weight $-\log r_{ab}$. Then a product greater than 1 corresponds to a sum of logarithms greater than 0, which is a **negative cycle**. Bellman–Ford finds it.

```python run
import math

def bellman_ford(vertices, edges, s):
    """edges: list of (u, v, w). Returns (dist, parent, cycle) where cycle is a negative cycle or None."""
    dist = {v: math.inf for v in vertices}
    parent = {v: None for v in vertices}
    dist[s] = 0
    for _ in range(len(vertices) - 1):
        changed = False
        for u, v, w in edges:
            if dist[u] + w < dist[v]:
                dist[v], parent[v] = dist[u] + w, u
                changed = True
        if not changed:
            break                                   # already final: stop early
    for u, v, w in edges:                           # the extra round
        if dist[u] + w < dist[v]:
            parent[v] = u
            x = v
            for _ in range(len(vertices)):          # walk back far enough to land on the cycle
                x = parent[x]
            cycle, y = [x], parent[x]
            while y != x:
                cycle.append(y)
                y = parent[y]
            return dist, parent, cycle[::-1]
    return dist, parent, None

# Made-up exchange rates: one unit of the first currency buys this many of the second.
rates = {("INR", "JPY"): 1.80, ("JPY", "EUR"): 0.0061, ("EUR", "INR"): 92.0,
         ("INR", "EUR"): 0.0108, ("EUR", "JPY"): 162.0, ("JPY", "INR"): 0.552}
currencies = sorted({c for pair in rates for c in pair})
edges = [(a, b, -math.log(r)) for (a, b), r in rates.items()]
_, _, cycle = bellman_ford(currencies, edges, "INR")
if cycle:
    loop = cycle + cycle[:1]
    gain = math.prod(rates[(a, b)] for a, b in zip(loop, loop[1:]))
    print("arbitrage:", " -> ".join(loop), f"multiplies money by {gain:.4f}")
else:
    print("no arbitrage")
```

<Narrator who="gideon">

Floating point can invent arbitrage. Rates of $0.1$, $0.1$ and $100$ around a triangle multiply to exactly 1, but the three weights $-\log r$ add up to about $-8.9 \times 10^{-16}$ in binary64, and `bellman_ford` duly reports a negative cycle. Real detectors compare against a tolerance and, more importantly, include fees and the gap between buying and selling prices, which can easily exceed a gain like the 1% found above.

</Narrator>

</Section>

<Section id="floyd-warshall" kind="human" title="All pairs: Floyd–Warshall">

Sometimes we need the distance between **every** pair of vertices: a table of travel times between all the depots of a delivery company, or the input to a clustering algorithm. Running Dijkstra from every vertex costs $O(V (V + E) \log V)$, which is the right choice for large sparse graphs with non-negative weights. For dense graphs, or graphs with negative edges, the **Floyd–Warshall** algorithm is simpler.

Number the vertices $1, \ldots, V$, and let $D_k[i][j]$ be the weight of the lightest path from $i$ to $j$ whose *intermediate* vertices all lie in $\{1, \ldots, k\}$. A best such path either avoids vertex $k$, or passes through it exactly once (assuming no negative cycles), splitting into a path $i \leadsto k$ and a path $k \leadsto j$ that use only intermediates below $k$:

$$D_k[i][j] = \min\big(D_{k-1}[i][j],\ D_{k-1}[i][k] + D_{k-1}[k][j]\big),$$

starting from $D_0$ = the edge weights (0 on the diagonal, $\infty$ where there is no edge). That is three nested loops, $k$ outermost, over a single $V \times V$ matrix updated in place: $O(V^3)$ time and $O(V^2)$ space. A negative entry on the diagonal at the end reveals a negative cycle. With Boolean values in place of numbers the same loops compute which vertices can reach which (Stephen Warshall's transitive closure, 1962). You will implement it in the exercises.

<Narrator who="chloe">

A way to see Bellman–Ford and Floyd–Warshall as one idea: take matrix multiplication and replace $\times$ by $+$ and $+$ by $\min$. In this *min-plus* algebra, the $k$-th power of the weight matrix holds the lightest paths with at most $k$ edges, so Bellman–Ford is that product taken one step at a time from a single row, and repeated squaring gives all pairs in $O(V^3 \log V)$. Floyd–Warshall's trick of growing the set of allowed intermediate vertices removes the $\log V$.

</Narrator>

</Section>

<Section id="astar" kind="human" title="A*: searching towards the goal">

Dijkstra from $s$ explores outwards in all directions, like a ripple in a pond, settling every vertex closer than the target before reaching it. When there is a single target $t$, most of that work is wasted: to drive from Lyon to Marseille, Dijkstra also settles every town around Lyon in the direction of Paris.

**A\*** (Hart, Nilsson and Raphael, 1968) adds a **heuristic** $h(v)$, an estimate of the remaining distance from $v$ to $t$, and orders the priority queue by $f(v) = d[v] + h(v)$: distance so far plus estimated distance to go. Vertices in the direction of the target get priority.

- $h$ is **admissible** if it never overestimates: $h(v) \le \delta(v, t)$ for every $v$. Then A* returns a shortest path.
- $h$ is **consistent** if $h(u) \le w(u, v) + h(v)$ for every edge, and $h(t) = 0$. Consistency implies admissibility, and then, like Dijkstra, A* never needs to settle a vertex twice.

The cleanest proof uses **reduced weights** $w'(u, v) = w(u, v) - h(u) + h(v)$. Consistency says exactly that $w' \ge 0$. Along any path from $s$ to $t$ the $h$ terms telescope, so every path's reduced weight equals its real weight minus $h(s)$ (since $h(t) = 0$): the *same* paths are shortest under both weightings. And A* on $w$ makes exactly the choices that Dijkstra makes on $w'$, which is correct because $w'$ is non-negative.

Good heuristics come from relaxing the problem. On a road map, the straight-line distance to the target is admissible for distances (no road is shorter than a straight line), and straight-line distance divided by the highest speed limit is admissible for travel times. On a grid where you move in four directions, the Manhattan distance $|x_1 - x_2| + |y_1 - y_2|$ is admissible. With $h = 0$, A* *is* Dijkstra; the closer $h$ is to the true distance, the fewer vertices it explores. Game engines use A* on grids and navigation meshes, and robot planners on maps of free space. Scaling $h$ up (weighted A*) explores even less but may return a slightly longer path.

```python run
import heapq

def grid_search(grid, start, goal, use_heuristic):
    """Shortest path length on a 4-connected grid ('#' = wall), and the number of cells settled."""
    rows, cols = len(grid), len(grid[0])
    def h(cell):
        return abs(cell[0] - goal[0]) + abs(cell[1] - goal[1]) if use_heuristic else 0
    dist, settled = {start: 0}, set()
    heap = [(h(start), start)]
    while heap:
        _, cell = heapq.heappop(heap)
        if cell in settled:
            continue
        settled.add(cell)
        if cell == goal:
            return dist[cell], len(settled)
        r, c = cell
        for nxt in ((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)):
            nr, nc = nxt
            if 0 <= nr < rows and 0 <= nc < cols and grid[nr][nc] != "#":
                if dist[cell] + 1 < dist.get(nxt, float("inf")):
                    dist[nxt] = dist[cell] + 1
                    heapq.heappush(heap, (dist[nxt] + h(nxt), nxt))
    return None, len(settled)

size = 60
grid = [["."] * size for _ in range(size)]
for r in range(5, 55):
    grid[r][30] = "#"                                # a long wall with gaps at both ends
start, goal = (30, 5), (30, 55)
for name, flag in [("Dijkstra", False), ("A* (Manhattan)", True)]:
    length, explored = grid_search(grid, start, goal, flag)
    print(f"{name:15} path length {length}, cells settled: {explored}")
```

Both find a path of the same length; A* settles far fewer cells, even though the wall forces it to look around.

<Narrator who="margaret">

Look at the counts more closely. The grid has $3600 - 50 = 3550$ open cells, and Dijkstra settled $3521$ of them: the goal, 100 steps away around the wall, is among the farthest cells from the start, so the ripple covers almost the whole map first. A* settled $1551$, under half. Delete the wall and try again: the Manhattan heuristic becomes exact, and A* settles just $51$ cells, the path itself, against Dijkstra's $2431$.

</Narrator>

<Section id="routing" kind="human" title="How routing services answer in milliseconds">

A continental road network has tens of millions of intersections. A well-implemented Dijkstra settles millions of them for a long-distance query and takes on the order of a second, and A* with straight-line distances helps less than you might hope: for travel times the estimate must assume the highest possible speed everywhere, which makes it weak. A routing service answering thousands of queries per second needs a different approach: do expensive work **once, in advance**, so that each query is cheap. The research community, often with industry co-authors, spent the 2000s on this problem, and the survey by Hannah Bast and colleagues ([2016](https://arxiv.org/abs/1504.05140)) records the outcome: queries on continental networks in well under a millisecond.

**Contraction hierarchies** (Geisberger, Sanders, Schultes and Delling, 2008) are the most widely used of these ideas, and simple to describe.

1. **Order** the vertices by importance, so that quiet residential corners come first and motorway junctions last. (Heuristics decide the order, for example by how many shortcuts a vertex would need.)
2. **Contract** the vertices one at a time in that order. Contracting $v$ removes it from the graph; for every pair of its remaining neighbours $u$ and $w$, a small local search looks for a *witness*, another path from $u$ to $w$ that is no longer than $u \to v \to w$. If there is none, add a **shortcut** edge $u \to w$ with the weight of $u \to v \to w$. Distances among the remaining vertices are preserved.
3. **Query** with a bidirectional Dijkstra, forwards from $s$ and backwards from $t$, in which each search only follows edges (original or shortcut) towards *more important* vertices. The two searches meet near the top of the hierarchy, after settling only hundreds of vertices instead of millions.

The trade-off is that preprocessing takes minutes and must be redone when weights change, which is awkward for live traffic. **Customisable route planning** (Delling, Goldberg, Pajor and Werneck, 2011) splits the work differently: partition the map into nested cells once, then, whenever traffic changes, recompute only the distances across each cell's boundary, which takes seconds. The open-source [OSRM](https://github.com/Project-OSRM/osrm-backend) engine offers both: contraction hierarchies, and a multi-level Dijkstra in the customisable style. Commercial services rarely document their exact methods, so treat any claim about a particular product with care; the published research and the open-source engines show the shape of the solution.

</Section>

<Section id="misconceptions" kind="misconceptions" title="Common misconceptions">

<Misconception>

**"Negative edges? Add a constant to every weight to make them positive."** This changes which path is shortest, because a path with more edges gains more of the constant. With edges $s \to t$ of weight 1 and $s \to a \to t$ of weights $-1$ and $1$, the two-edge path is shorter (0 against 1); add 2 to every edge and it becomes longer (4 against 3). Reweighting that *does* preserve shortest paths must use vertex potentials, as A*'s reduced weights do (Johnson's all-pairs algorithm computes such potentials with Bellman–Ford).

</Misconception>

<Misconception>

**"Dijkstra works with negative edges if you let it re-settle vertices."** Then it is no longer Dijkstra: with negative edges such a "label-correcting" variant can take exponential time on some graphs. Use Bellman–Ford, or reweight first.

</Misconception>

<Misconception>

**"A* is always faster than Dijkstra."** It is never worse in vertices settled when the heuristic is consistent, but a weak heuristic saves little and adds the cost of computing $h$ for every vertex. An *inadmissible* heuristic can be faster still, at the price of returning a path that is not shortest.

</Misconception>

<Misconception>

**"Longest paths are just shortest paths with negated weights."** Negating turns every cycle of positive weight into a negative cycle, and the longest *simple* path problem is NP-hard in general (it contains the Hamiltonian path problem). In a DAG there are no cycles, and longest paths are easy: relax edges in topological order. Project managers do exactly this to find a schedule's *critical path*.

</Misconception>

</Section>
