<Section id="motivation" kind="motivation" title="Why would an algorithm flip coins?">

An algorithm is supposed to be a precise recipe. Why would anyone put a coin toss into one? Three reasons keep coming up.

**Randomness defeats adversaries.** Quicksort that always picks the first element as its pivot is quadratic on already-sorted input, and sorted input is common. Pick the pivot at random and *no* input is bad any more: the slow cases still exist, but they depend on the coin flips, which nobody outside can predict or arrange. The same idea protects hash tables from attackers who would otherwise send keys that all collide.

**Randomness makes hard things simple.** Choosing a random sample, spreading requests over servers, or testing whether a 600-digit number is prime all have simple randomised solutions where the deterministic ones are complicated or slow.

**Randomness lets a small memory summarise a huge stream.** A website wants to know how many *different* visitors it had today, out of a billion page views. Remembering every visitor takes gigabytes. A HyperLogLog sketch answers within a couple of per cent using a few kilobytes, by looking at random-looking bits of hashed IDs.

Throughout this lesson, "random" means the algorithm's *own* coin flips. We make no assumption that the input is random; the guarantees hold for every input, on average over the coins. That distinction, between average over the algorithm's choices and average over inputs, is the heart of the subject.

</Section>

<Section id="definitions" kind="definitions" title="Las Vegas and Monte Carlo">

<Definition term="randomised algorithm">

A **randomised algorithm** may call a source of random bits. Its running time, and possibly its output, are then random variables, and we analyse them for a **fixed, worst-case input**, with probability taken over the random bits only.

</Definition>

<Definition term="Las Vegas, Monte Carlo">

A **Las Vegas** algorithm always returns a correct answer; only its running time is random, and we bound its **expected** running time. A **Monte Carlo** algorithm has a bounded running time but may return a wrong answer with some bounded probability. It has **one-sided error** if it can err only in one direction (for example, it may say "composite" only when the number really is composite, but may wrongly say "prime").

</Definition>

Randomised quicksort is Las Vegas: always sorted, sometimes slower. Rabin–Karp with its verification step, from <LessonLink slug="string-algorithms">String algorithms</LessonLink>, is Las Vegas too; drop the verification and it becomes Monte Carlo. The **Miller–Rabin** primality test is Monte Carlo with one-sided error: a "composite" verdict is always right, and a composite number passes one round with probability at most $1/4$. Cryptographic libraries use it to generate the large primes behind RSA keys. **Freivalds' algorithm** checks whether $AB = C$ for $n \times n$ matrices by multiplying both sides by a random 0/1 vector, costing $O(n^2)$ instead of a full multiplication; a wrong $C$ survives a trial with probability at most $1/2$.

<Theorem name="Amplification">

If a Monte Carlo algorithm with one-sided error is wrong with probability at most $p$ on each run, and runs use independent random bits, then running it $t$ times and answering "composite" (say) if *any* run does, errs with probability at most $p^t$.

</Theorem>

<Proof>

The combined answer is wrong only if every one of the $t$ runs is wrong. The runs are independent, so the probability of that is the product of the individual probabilities, at most $p^t$.

</Proof>

Forty rounds of Miller–Rabin leave an error probability below $4^{-40} \approx 10^{-24}$, far smaller than the chance of a hardware fault during the computation. Two more conversions are worth knowing. A Las Vegas algorithm becomes Monte Carlo by stopping it at, say, three times its expected running time and answering "don't know"; by Markov's inequality that happens with probability at most $1/3$. A Monte Carlo algorithm becomes Las Vegas if you can check its answer cheaply and repeat until the check passes.

</Section>

<Section id="quicksort" kind="examples" title="Randomised quicksort, analysed">

You met quicksort in <LessonLink slug="searching-and-sorting">Searching and sorting</LessonLink>: pick a pivot, partition the rest into smaller and larger elements, recurse. With a uniformly random pivot, how many comparisons does it make?

<Theorem name="Expected comparisons of randomised quicksort">

On any input of $n$ distinct keys, randomised quicksort makes at most $2 n H_n \le 2 n \ln n + 2n$ comparisons in expectation, where $H_n = 1 + \tfrac12 + \cdots + \tfrac1n$. (The exact expectation is $2(n+1)H_n - 4n$.)

</Theorem>

<Proof>

Name the keys in sorted order $z_1 \lt z_2 \lt \cdots \lt z_n$. Two keys are compared only when one of them is the current pivot, and a pivot is never compared again after its partition, so each pair is compared at most once. Let $X_{ij}$ be 1 if $z_i$ and $z_j$ are compared ($i \lt j$) and 0 otherwise; the total number of comparisons is $X = \sum_{i \lt j} X_{ij}$.

Consider the block $Z_{ij} = \{z_i, z_{i+1}, \ldots, z_j\}$, which has $j - i + 1$ keys. As long as no pivot has been chosen from inside $Z_{ij}$, all of its keys stay together in one subarray. The first pivot chosen from $Z_{ij}$ decides the pair's fate: if it is $z_i$ or $z_j$, the two are compared; if it is any key strictly between them, they are separated into different subarrays and never meet. Because pivots are uniform over the current subarray, every key of $Z_{ij}$ is equally likely to be that first pivot. So $\Pr[X_{ij} = 1] = 2/(j - i + 1)$, and by linearity of expectation,

$$\mathbb{E}[X] = \sum_{i=1}^{n-1} \sum_{j=i+1}^{n} \frac{2}{j-i+1} \le \sum_{i=1}^{n-1} \sum_{d=2}^{n} \frac{2}{d} \lt 2 n H_n.$$

Since $H_n \le \ln n + 1$, this is at most $2n \ln n + 2n$.

</Proof>

Linearity of expectation did the heavy lifting: the $X_{ij}$ are far from independent, but expectations add regardless. Lumenary Math's <TopicLink id="math.prob.probability-rules">Conditional probability and independence</TopicLink> lesson covers the probability used here.

```python run
import math, random

def quicksort(a, choose_pivot):
    """In-place quicksort with an explicit stack; returns the sorted list and the comparison count."""
    a, comparisons = list(a), 0
    stack = [(0, len(a) - 1)]
    while stack:
        lo, hi = stack.pop()
        if lo >= hi:
            continue
        p = choose_pivot(lo, hi)
        a[p], a[hi] = a[hi], a[p]           # move the pivot to the end, then partition
        pivot, i = a[hi], lo
        for j in range(lo, hi):
            comparisons += 1
            if a[j] < pivot:
                a[i], a[j] = a[j], a[i]
                i += 1
        a[i], a[hi] = a[hi], a[i]
        stack += [(lo, i - 1), (i + 1, hi)]
    return a, comparisons

n = 2000
already_sorted = list(range(n))

_, c = quicksort(already_sorted, lambda lo, hi: lo)       # deterministic: first element as pivot
print(f"first-element pivot on sorted input: {c:,} comparisons (n(n-1)/2 = {n * (n - 1) // 2:,})")

rng = random.Random(1)
counts = []
for trial in range(20):
    result, c = quicksort(already_sorted, lambda lo, hi: rng.randint(lo, hi))
    assert result == already_sorted
    counts.append(c)
harmonic = sum(1 / k for k in range(1, n + 1))
print(f"random pivot, 20 runs: min {min(counts):,}, mean {sum(counts) / len(counts):,.0f}, max {max(counts):,}")
print(f"exact expectation 2(n+1)H_n - 4n = {2 * (n + 1) * harmonic - 4 * n:,.0f};  2n ln n = {2 * n * math.log(n):,.0f}")
```

On sorted input the deterministic version makes about two million comparisons, eighty times more than the randomised one. Notice also how tightly the twenty random runs cluster around the expectation. That is not luck: the number of comparisons is *concentrated*, and the probability of exceeding the expectation by a constant factor falls off faster than any power of $n$. "Expected $O(n \log n)$" is, in practice, a promise.

</Section>

<Section id="reservoir" kind="computation" title="Sampling a stream: reservoir sampling">

A server writes a billion log lines a day, and you want 1,000 chosen uniformly at random, in one pass, without knowing in advance how many lines there will be and without storing them. **Reservoir sampling** (Algorithm R, analysed by Vitter in 1985) does it with memory for just the sample:

1. Keep the first $k$ items.
2. When item number $t$ arrives ($t \gt k$), pick a random integer $j$ from $1$ to $t$. If $j \le k$, the new item replaces the $j$-th item of the reservoir; otherwise discard it.

<Theorem name="Reservoir sampling is uniform">

After $t \ge k$ items, each of them is in the reservoir with probability exactly $k/t$.

</Theorem>

<Proof>

By induction on $t$. For $t = k$ every item is kept: probability $k/k = 1$. Suppose the claim holds after $t$ items, and item $t+1$ arrives. It enters with probability $k/(t+1)$, as required. An earlier item was in the reservoir with probability $k/t$; it is evicted only if the new item enters *and* lands on its slot, which happens with probability $\frac{k}{t+1} \cdot \frac1k = \frac{1}{t+1}$. So it is still there with probability $\frac{k}{t}\left(1 - \frac{1}{t+1}\right) = \frac{k}{t} \cdot \frac{t}{t+1} = \frac{k}{t+1}$.

</Proof>

A slightly longer induction shows more: every *set* of $k$ items is equally likely to be the reservoir, so it is a genuinely uniform sample, not just one with the right marginal probabilities.

```python run
import random
from collections import Counter

def reservoir_sample(stream, k, rng):
    """A uniform random sample of k items from a stream of unknown length, in one pass and O(k) memory."""
    sample = []
    for i, item in enumerate(stream):          # item i is the (i+1)-th item seen
        if i < k:
            sample.append(item)
        else:
            j = rng.randrange(i + 1)           # uniform in 0..i
            if j < k:                          # happens with probability k/(i+1)
                sample[j] = item
    return sample

def log_lines():
    """A stand-in for a stream too long to store: we never know its length in advance."""
    cities = ["Accra", "Bogotá", "Chennai", "Dhaka", "Hanoi", "Manila", "Nairobi", "Seoul"]
    for i in range(1, 100_001):
        yield f"request {i:6} from {cities[(i * 7) % len(cities)]}"

rng = random.Random(2024)
for line in reservoir_sample(log_lines(), 4, rng):
    print(line)

# Is it really uniform? Sample 3 of 10 items many times and count how often each is chosen.
tally = Counter()
trials = 30_000
for _ in range(trials):
    tally.update(reservoir_sample(range(10), 3, rng))
print({item: round(tally[item] / trials, 3) for item in range(10)}, "(each should be near 0.3)")
```

The same pattern, keep a few items and replace them with carefully chosen probabilities, extends to weighted sampling (one of the exercises), to sampling over a sliding time window, and to distributed sampling where each machine keeps a reservoir and the reservoirs are merged.

</Section>

<Section id="load" kind="human" title="Hashing to spread the load">

Hash functions turn up whenever work must be divided: which of 50 cache servers holds a user's session, which shard of a database stores a row, which bucket of a <LessonLink slug="hash-tables">hash table</LessonLink> holds a key. A good hash behaves like a random function, so each key lands on a uniformly random server, independently of the others. Placing $n$ keys on $m$ servers is then the **balls-into-bins** experiment. The average load is $n/m$; when $n = m$, the busiest server gets about $\ln n / \ln \ln n$ keys, a slowly growing but real imbalance. A surprising improvement, the **power of two choices**: hash each key to *two* random servers and put it on the less loaded one. The maximum load drops to about $\ln \ln n / \ln 2$, exponentially better, and load balancers use this idea to pick between two random back ends.

**Adversaries again.** As <LessonLink slug="hash-tables">Hash tables</LessonLink> showed with hash flooding, a fixed, public hash function lets an attacker choose keys that all collide. The defence is randomness again: choose the hash function *at random* when the program starts, from a family where any two distinct keys collide with probability about $1/m$ (Carter and Wegman's **universal hashing**, 1979). That is why Python's `hash()` of a string changes from one run to the next (PEP 456). A practical consequence: never use `hash()` for anything stored on disk or shared between processes. Use `hashlib`, as every runnable block in this lesson does.

**Changing the number of servers.** The naive assignment `server = h(key) % m` has a nasty property: when $m$ changes from 10 to 11, a key stays put only if $h \bmod 10 = h \bmod 11$, which holds for only about one key in 11. Ninety per cent of the keys move, and a cache cluster that adds one machine loses almost all its contents at once. Two schemes fix this:

- **Consistent hashing** (Karger and colleagues, 1997) places both servers and keys at hashed positions on a circle; each key belongs to the next server clockwise. Adding a server takes over only the keys between it and its predecessor, about $1/m$ of them. It underlies many distributed caches and databases you will meet in <LessonLink slug="distributed-systems">Distributed systems</LessonLink>.
- **Rendezvous hashing** (highest random weight; Thaler and Ravishankar, 1998) is even simpler: for each key, compute a hash of the pair (server, key) for every server and pick the server with the highest score. Removing a server moves only its own keys; adding one moves only the keys it now wins. You will implement it in the exercises.

</Section>

<Section id="bloom" kind="examples" title="Bloom filters: membership with a small lie">

A database keeps data in hundreds of files on disk. Before reading a file to look for a key, it would like to know whether the key could possibly be there. A **Bloom filter** answers "definitely not" or "probably yes" using about ten bits per key, whatever the size of the keys.

<Definition term="Bloom filter">

A **Bloom filter** is an array of $m$ bits, all initially 0, with $k$ hash functions $h_1, \ldots, h_k$ mapping items to positions $0, \ldots, m-1$. To **add** an item, set the $k$ bits $h_1(x), \ldots, h_k(x)$ to 1. To **query** an item, answer "probably present" if all $k$ of its bits are 1, and "absent" otherwise.

</Definition>

An item that was added always has all its bits set, so there are **no false negatives**. A **false positive** happens when an item that was never added finds all its $k$ bits set by other items. After $n$ insertions, a particular bit is still 0 with probability $(1 - 1/m)^{kn} \approx e^{-kn/m}$, so (treating bits as independent, which is accurate for realistic sizes) the false-positive rate is

$$p \approx \left(1 - e^{-kn/m}\right)^k.$$

More hash functions set more bits per item but also check more bits per query; the rate is minimised at $k = \frac{m}{n} \ln 2$, where half the bits are set, giving $p \approx 0.6185^{m/n}$. Turned around: a 1% false-positive rate needs about $1.44 \log_2(1/p) \approx 9.6$ bits per item, and every further 4.8 bits per item cuts the rate by ten.

```python run
import hashlib, math

class BloomFilter:
    def __init__(self, m_bits, k):
        self.m, self.k = m_bits, k
        self.bits = bytearray((m_bits + 7) // 8)

    def _positions(self, item):
        # Two 64-bit hashes from one digest; the k positions are h1 + i*h2 (Kirsch and Mitzenmacher).
        d = hashlib.blake2b(item.encode(), digest_size=16).digest()
        h1, h2 = int.from_bytes(d[:8], "little"), int.from_bytes(d[8:], "little") | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, item):
        for p in self._positions(item):
            self.bits[p // 8] |= 1 << (p % 8)

    def __contains__(self, item):
        return all(self.bits[p // 8] >> (p % 8) & 1 for p in self._positions(item))

n = 10_000                          # items we will insert
for bits_per_item in (4, 8, 10, 16):
    m = bits_per_item * n
    k = max(1, round(bits_per_item * math.log(2)))     # the optimal number of hash functions
    bf = BloomFilter(m, k)
    for i in range(n):
        bf.add(f"user-{i}")
    assert all(f"user-{i}" in bf for i in range(n))     # never a false negative
    probes = 50_000
    false_pos = sum(f"stranger-{i}" in bf for i in range(probes))
    predicted = (1 - math.exp(-k * n / m)) ** k
    print(f"{bits_per_item:2} bits/item, k={k:2}: false positives {false_pos / probes:.4f}, "
          f"formula {predicted:.4f}, memory {len(bf.bits):,} bytes for {n:,} items")
```

Ten thousand keys in 12.5 kilobytes with under 1% false positives, regardless of whether the keys are short IDs or long URLs. Computing $k$ independent hashes is the expensive part, so the code uses a trick of Kirsch and Mitzenmacher: two hashes $h_1, h_2$ generate all $k$ positions as $h_1 + i h_2$, with no measurable loss.

Where they live: databases built on log-structured merge trees, such as RocksDB and Cassandra, keep a Bloom filter for every on-disk file and skip any file the filter rules out, which saves most of the disk reads for keys that are absent (more in <LessonLink slug="databases">Databases</LessonLink>). Standard Bloom filters cannot delete items, since clearing a bit might erase evidence of another item; counting Bloom filters and cuckoo filters support deletion at some extra cost.

</Section>

<Section id="sketches" kind="computation" title="Sketches: counting without remembering">

A **sketch** is a small summary of a stream that answers one kind of question approximately, with error bounds that hold with high probability. Two are worth knowing by heart.

### Count-min: how often did this item appear?

A **count-min sketch** keeps $d$ rows of $w$ counters, with an independent hash function per row. To add an item, increment one counter in each row, the one its row's hash selects. To estimate an item's count, take the **minimum** of its $d$ counters. Each counter holds the item's true count plus the counts of whatever else collided there, so every row overestimates, and the minimum is the least-polluted row.

<Theorem name="Count-min error bound">

Let $N$ be the total of all counts. With $w = \lceil e/\varepsilon \rceil$ columns and $d = \lceil \ln(1/\delta) \rceil$ rows, every estimate is at least the true count, and exceeds it by more than $\varepsilon N$ with probability at most $\delta$.

</Theorem>

<Proof>

Fix an item and one row. The excess in its counter is the total count of other items hashed to the same column. Each other item lands there with probability $1/w$ (for a pairwise-independent hash), so the expected excess is at most $N/w \le \varepsilon N / e$. By Markov's inequality, the excess exceeds $\varepsilon N$ with probability at most $1/e$. The rows use independent hash functions, so all $d$ rows exceed it, which is what it takes for the minimum to exceed it, with probability at most $e^{-d} \le \delta$.

</Proof>

The guarantee is relative to the *total* $N$, so count-min is accurate for frequent items ("heavy hitters": the most-requested URLs, the busiest IP addresses) and nearly useless for rare ones, which is usually what you want.

### HyperLogLog: how many different items?

Counting *distinct* items is harder, because you cannot tell whether you have seen an item before without remembering it. The insight of Flajolet and Martin (1985), refined into **HyperLogLog** (2007): hash each item to a string of random-looking bits. A hash that begins with $\rho - 1$ zeros and then a 1 occurs with probability $2^{-\rho}$, so if the largest such $\rho$ seen so far is 20, you have probably seen around a million distinct items. Repeats do not matter, since an item hashes the same way every time. One such maximum is very noisy, so HyperLogLog uses the first $b$ bits of the hash to pick one of $m = 2^b$ registers, keeps a separate maximum in each, and combines them with a bias-corrected harmonic mean. The standard error is about $1.04/\sqrt{m}$, and each register needs only 6 bits.

```python run
import hashlib, math, random
from collections import Counter

def h64(item, seed=0):
    """A 64-bit hash of a string; different seeds give independent-looking hash functions."""
    d = hashlib.blake2b(item.encode(), digest_size=8, salt=seed.to_bytes(16, "little")).digest()
    return int.from_bytes(d, "big")

class CountMin:
    def __init__(self, width, depth):
        self.w, self.d = width, depth
        self.rows = [[0] * width for _ in range(depth)]

    def add(self, item, count=1):
        for r in range(self.d):
            self.rows[r][h64(item, r) % self.w] += count

    def estimate(self, item):
        return min(self.rows[r][h64(item, r) % self.w] for r in range(self.d))   # never too low

class HyperLogLog:
    def __init__(self, b=10):
        self.b, self.m = b, 1 << b
        self.reg = [0] * self.m

    def add(self, item):
        x = h64(item, 99)
        j = x >> (64 - self.b)                       # the first b bits pick a register
        rest = x & ((1 << (64 - self.b)) - 1)
        rank = (64 - self.b) - rest.bit_length() + 1 # position of the first 1-bit in the rest
        self.reg[j] = max(self.reg[j], rank)

    def estimate(self):
        m = self.m
        raw = 0.7213 / (1 + 1.079 / m) * m * m / sum(2.0 ** -r for r in self.reg)
        zeros = self.reg.count(0)
        if raw <= 2.5 * m and zeros:                 # small counts: linear counting is better
            return m * math.log(m / zeros)
        return raw

# A stream of page views where popularity follows a power law, as on real websites.
rng = random.Random(5)
pages = [f"/page/{r}" for r in range(1, 20_001)]
weights = [1 / r for r in range(1, 20_001)]
stream = rng.choices(pages, weights, k=60_000)

truth = Counter(stream)
cms, hll = CountMin(width=1000, depth=4), HyperLogLog(b=10)
for page in stream:
    cms.add(page)
    hll.add(page)

print("count-min sketch (4 x 1000 counters):")
for page, true_count in truth.most_common(3) + [("/page/5000", truth["/page/5000"])]:
    print(f"   {page:11} true {true_count:5}, estimate {cms.estimate(page):5}")
print(f"   error bound e/w * N = {math.e / 1000 * len(stream):.0f} (holds with probability >= 1 - e^-4)")
print(f"HyperLogLog (1024 registers of a few bits): distinct pages true {len(truth):,}, "
      f"estimate {hll.estimate():,.0f}  (typical error 1.04/sqrt(1024) = {1.04 / 32:.1%})")
```

The popular pages are estimated within about 1%; the rare page is overestimated by a couple of dozen, well inside the bound. The HyperLogLog, using 1,024 small registers, lands within a few per cent of the true number of distinct pages. Both sketches are **mergeable**: two count-min sketches with the same hash functions add counter by counter, and two HyperLogLogs merge by taking the maximum of each register. So a thousand servers can each sketch their own traffic and a central service can combine them, which is how these structures are used at scale. Redis offers HyperLogLog with 12 KB per counter and a standard error of 0.81%, and analytics databases offer `APPROX_COUNT_DISTINCT`-style functions built on HyperLogLog variants.

</Section>

<Section id="seeds" kind="human" title="Seeded randomness and real randomness">

Computers usually do not flip real coins. Python's `random` module is a **pseudorandom number generator** (the Mersenne Twister): a deterministic function that turns a starting **seed** into a long sequence that passes statistical tests for randomness. That determinism is a feature for engineering:

- **Reproducibility.** Every runnable block in this lesson creates its own `random.Random(seed)`, so it prints the same thing every time, here and in Lumenary's test suite. Record the seed of every simulation and experiment; a result you cannot reproduce is a result you cannot debug. (NumPy's equivalent is `numpy.random.default_rng(seed)`.)
- **Isolation.** A private `random.Random` instance, rather than the module-level functions, keeps one component's randomness from shifting another's.
- **Testing randomised code.** Fix the seed in unit tests, and for statistical properties test with tolerances over many trials, as the reservoir demo did.

Pseudorandomness is the wrong tool for **secrets**. The Mersenne Twister's entire future output can be computed from 624 consecutive 32-bit outputs, so session tokens, password-reset links and keys generated with `random` can be predicted. Use the `secrets` module (or `os.urandom`), which draws on the operating system's cryptographically secure generator; <LessonLink slug="applied-cryptography">Applied cryptography</LessonLink> explains what "cryptographically secure" means.

</Section>

<Section id="misconceptions" kind="misconceptions" title="Common misconceptions">

<Misconception>

**"A randomised algorithm assumes random input."** It assumes nothing about the input. Average-case analysis of a *deterministic* algorithm averages over inputs and can be defeated by a bad input; a randomised algorithm's guarantees hold for every input, averaged over its own coins.

</Misconception>

<Misconception>

**"Randomised means unreliable."** Las Vegas algorithms are always correct. Monte Carlo error can be driven below the rate of hardware faults by a few repetitions. And for quicksort, the running time is so concentrated that a slow run is less likely than a cosmic-ray bit flip.

</Misconception>

<Misconception>

**"A Bloom filter can say an item is absent when it is present."** Never: an added item's bits stay set. Errors go only the other way. (A filter that supports deletion by clearing bits would break this, which is why deletion needs a different design.)

</Misconception>

<Misconception>

**"`hash(s)` is a stable fingerprint of a string."** It changes from one run of Python to the next, by design. Use `hashlib` for anything that must be stable.

</Misconception>
