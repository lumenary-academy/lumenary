<Section id="motivation" kind="motivation" title="When the list of kinds is open">

Lesson 4 modelled "a search result that may or may not have found something" with a discriminated record: two variants, fixed forever, handled with `case`. That is the right tool when the set of kinds is **closed** and known in advance. Every `case` can list them all, and the compiler checks it.

Sometimes the set is **open**. A railway operator's software handles locomotives, coaches and wagons today, and next year a new kind of vehicle arrives, perhaps added by another team that cannot edit your code. A logging system must accept events from subsystems that do not exist yet. Here you want code that works with "any vehicle" or "any loggable thing", and each kind brings its own behaviour with it. That is what object-oriented programming is for, and since Ada 95 Ada has supported it through **tagged types**.

Ada's object orientation looks different from Java's or Python's because it is built from parts you already know. There is no `class` keyword. A "class" in the usual sense is a **package** that declares a **tagged record type** and the subprograms that operate on it; inheritance is **type extension**; and the information hiding you learnt in Lesson 5 works exactly as before.

</Section>

<Section id="definitions" kind="definitions" title="Tagged types, primitives and dispatching">

<Definition term="Tagged type">

A record type declared `tagged` carries a hidden **tag** at run time that identifies its specific type. A tagged type can be **extended**: `type Coach is new Vehicle with record … end record;` declares a new type with all of `Vehicle`'s components plus new ones.

</Definition>

<Definition term="Primitive operation">

A subprogram declared in the same package specification as a tagged type, with a parameter (or result) of that type, is a **primitive operation** of the type. Extensions **inherit** every primitive and may **override** it with their own version, marked `overriding`.

</Definition>

<Definition term="Class-wide type and dispatching">

For a tagged type `T`, the **class-wide type** `T'Class` covers `T` and every type ever derived from it. A call to a primitive operation with a class-wide argument **dispatches**: at run time, the tag selects the version belonging to the argument's specific type.

</Definition>

The distinction between specific and class-wide types is the key to Ada OO. A parameter of type `Vehicle` accepts only a `Vehicle`; a parameter of type `Vehicle'Class` accepts any vehicle. Calls on a specific type are bound at compile time, which is cheap and predictable; only calls on class-wide values dispatch. In Java every method call may dispatch; in Ada you can see from the types exactly where dynamic binding happens, which matters to people who must analyse worst-case timing.

Three more pieces complete the picture:

- An **abstract** type (`type Vehicle is abstract tagged …`) cannot have objects of its own, only of its extensions. An abstract subprogram (`… is abstract;`) has no body, and every non-abstract extension must override it.
- An **interface** (Ada 2005) is an abstract tagged type with no components. A type may extend one parent and implement any number of interfaces: `type Door_Opened is new Event and Loggable with …`.
- **Prefixed notation**: `V.Describe` means `Describe (V)`. It works for any primitive operation and reads like method calls in other languages.

</Section>

<Section id="examples" kind="examples" title="Rolling stock">

```ada check
pragma Ada_2022;
with Ada.Text_IO; use Ada.Text_IO;
with Ada.Containers.Indefinite_Vectors;

procedure Main is

   package Rolling_Stock is
      type Tonnes is range 0 .. 10_000;

      --  The root type: tagged, so it can be extended and dispatched on.
      type Vehicle is abstract tagged record
         Empty_Mass : Tonnes;
      end record;

      --  Primitive operations: declared with the type, inherited by extensions.
      function Mass (V : Vehicle) return Tonnes is (V.Empty_Mass);
      function Seats (V : Vehicle) return Natural is (0);
      function Describe (V : Vehicle) return String is abstract;

      type Locomotive is new Vehicle with record
         Kilowatts : Positive;
      end record;
      overriding function Describe (L : Locomotive) return String;

      type Coach is new Vehicle with record
         Seat_Count : Natural;
      end record;
      overriding function Seats (C : Coach) return Natural is (C.Seat_Count);
      overriding function Describe (C : Coach) return String;

      type Wagon is new Vehicle with record
         Cargo : Tonnes;
      end record;
      overriding function Mass (W : Wagon) return Tonnes is (W.Empty_Mass + W.Cargo);
      overriding function Describe (W : Wagon) return String;
   end Rolling_Stock;

   package body Rolling_Stock is
      function Describe (L : Locomotive) return String is
        ("locomotive," & L.Kilowatts'Image & " kW");
      function Describe (C : Coach) return String is
        ("coach," & C.Seat_Count'Image & " seats");
      function Describe (W : Wagon) return String is
        ("wagon carrying" & W.Cargo'Image & " t");
   end Rolling_Stock;

   use Rolling_Stock;

   --  A vector of any vehicle: elements are of the class-wide type Vehicle'Class.
   package Trains is new Ada.Containers.Indefinite_Vectors
     (Index_Type => Positive, Element_Type => Vehicle'Class);

   Train       : Trains.Vector;
   Total_Mass  : Tonnes := 0;
   Total_Seats : Natural := 0;
begin
   Train.Append (Locomotive'(Empty_Mass => 84, Kilowatts => 4_200));
   Train.Append (Coach'(Empty_Mass => 46, Seat_Count => 64));
   Train.Append (Coach'(Empty_Mass => 48, Seat_Count => 56));
   Train.Append (Wagon'(Empty_Mass => 22, Cargo => 58));

   for V of Train loop
      Put_Line (V.Describe & ", mass" & V.Mass'Image & " t");   -- dispatching calls
      Total_Mass  := Total_Mass + V.Mass;
      Total_Seats := Total_Seats + V.Seats;
   end loop;
   Put_Line ("Train:" & Total_Mass'Image & " t," & Total_Seats'Image & " seats");
end Main;
```

It prints:

```text
locomotive, 4200 kW, mass 84 t
coach, 64 seats, mass 46 t
coach, 56 seats, mass 48 t
wagon carrying 58 t, mass 80 t
Train: 258 t, 120 seats
```

Walk through the design:

- `Vehicle` is abstract and tagged. It declares three primitives: `Mass` and `Seats` with default behaviour, and `Describe`, abstract, so every kind of vehicle must say how it describes itself.
- `Coach` overrides `Seats`, `Wagon` overrides `Mass` (a loaded wagon is heavier than its empty mass), and all three override `Describe`. The `Locomotive` inherits `Mass` and `Seats` unchanged.
- `Trains` is an `Indefinite_Vectors` instance whose element type is `Vehicle'Class`. Values of different specific types, with different sizes, sit in one vector without any pointers in your code.
- In the loop, `V` is a `Vehicle'Class` element, so `V.Describe`, `V.Mass` and `V.Seats` dispatch on its tag.
- `Locomotive'(…)` is a qualified aggregate: it names the specific type being built, since an aggregate on its own does not say which extension it is.

The `overriding` indicator is optional in the language but universal in professional code, because it turns a classic silent bug into a compile error. Misspell `Describe` as `Describ` in `Coach` and GNAT 14 reports:

```text
main.adb:25:12: error: type must be declared abstract or "Describe" overridden
main.adb:25:12: error: "Describe" has been inherited from subprogram at line 18
main.adb:29:18: error: subprogram "Describ" is not overriding
```

In a language without such a check, the misspelt function would compile as a new, unrelated method, and coaches would quietly use the parent's behaviour. (Ada also has `not overriding`, to state that a subprogram is meant to be new.)

You can ask about a value's type at run time with a membership test: `if V in Coach'Class then` is true for coaches and anything derived from them. Experienced programmers use such tests sparingly: a chain of them is usually a sign that the behaviour belongs in a primitive operation.

</Section>

<Section id="intuition" kind="intuition" title="Calling the parent, and building extensions">

Two everyday questions come up as soon as you write extensions. How does an overriding operation reuse the parent's version, as `super.describe()` would in Java? And how do you build a value of an extension when the parent's part already exists? Ada answers both with conversions and aggregates rather than new keywords:

```ada check
pragma Ada_2022;
with Ada.Text_IO; use Ada.Text_IO;

procedure Main is
   package Accounts is
      type Campus is (Makerere, UNAM, Tsinghua);

      type Account is tagged record
         Number  : Positive;
         Balance : Integer := 0;     -- in cents
      end record;
      function Describe (A : Account) return String;
      function Monthly_Fee (A : Account) return Integer is (200);

      type Student_Account is new Account with record
         School : Campus;
      end record;
      overriding function Describe (S : Student_Account) return String;
      overriding function Monthly_Fee (S : Student_Account) return Integer is (0);

      procedure Charge_Fee (A : in out Account'Class);
   end Accounts;

   package body Accounts is
      function Describe (A : Account) return String is
        ("account" & A.Number'Image & ", balance" & A.Balance'Image);

      function Describe (S : Student_Account) return String is
        (Describe (Account (S)) & ", student at " & S.School'Image);  -- parent's version

      procedure Charge_Fee (A : in out Account'Class) is
      begin
         A.Balance := A.Balance - A.Monthly_Fee;                    -- dispatches
      end Charge_Fee;
   end Accounts;

   use Accounts;

   Plain : Account := (Number => 1001, Balance => 10_000);
   Ines  : Student_Account :=
     (Account'(Number => 1002, Balance => 5_000) with School => UNAM);
begin
   Charge_Fee (Plain);
   Charge_Fee (Ines);
   Put_Line (Plain.Describe);
   Put_Line (Ines.Describe);
   Put_Line (Account (Ines).Describe);
end Main;
```

It prints:

```text
account 1001, balance 9800
account 1002, balance 5000, student at UNAM
account 1002, balance 5000
```

- **Calling the parent.** Inside `Describe` for `Student_Account`, the expression `Account (S)` is a **view conversion**: it does not copy anything, it just looks at `S` as an `Account`. Because that view has the *specific* type `Account`, the call `Describe (Account (S))` is bound statically to the parent's version. The last line of the main program does the same thing from outside, which is why it prints no school.
- **Class-wide operations that dispatch.** `Charge_Fee` takes `Account'Class`, so `A.Monthly_Fee` dispatches: the plain account pays 200 cents, the student account nothing. Writing such operations once, class-wide, and letting the primitives vary is the Ada form of the *template method* design pattern.
- **Extension aggregates.** `(Account'(Number => 1002, Balance => 5_000) with School => UNAM)` builds a `Student_Account` from a value of the parent type plus the new components. The parent part can be any expression of the parent type, such as the result of a function, which is how Ada programmers write "constructors": ordinary functions that return a fully initialised object.

<Narrator who="gideon">

The same rule surprises Java programmers from the other side: inside a primitive, a call on a parameter of the *specific* type does not dispatch again. Give the rolling stock a primitive `function Report (V : Vehicle) return String is ("mass" & Mass (V)'Image);` and `V.Report` on the wagon prints `mass 22`, its empty mass, because `Mass (V)` was bound to `Vehicle`'s version. To redispatch, convert to the class-wide type, `Vehicle'Class (V).Mass`, and it prints `mass 80`.

</Narrator>

Ada has no special constructor syntax. A function such as `function Create (Number : Positive) return Account` does the job. Declare the type as `type Account (<>) is private;`, with **unknown discriminants**, and clients cannot even declare an object without initialising it from one of these functions, so every object starts valid. If a type must never be copied, make it limited as well: since Ada 2005 such functions build the object in place, without a copy.

</Section>

<Section id="computation" kind="computation" title="Interfaces and controlled types">

### Interfaces

An interface describes a capability that unrelated types can share. Here two kinds of event extend a common `Event` type and also implement `Loggable`, and a class-wide procedure logs any `Loggable` without knowing the event types:

```ada check
pragma Ada_2022;
with Ada.Text_IO; use Ada.Text_IO;

procedure Main is

   package Logging is
      --  An interface: operations only, no data. A type may implement several.
      type Loggable is interface;
      function Log_Line (Item : Loggable) return String is abstract;
      function Severity (Item : Loggable) return Natural is abstract;

      procedure Log (Item : Loggable'Class);   -- class-wide: works for any Loggable
   end Logging;

   package body Logging is
      procedure Log (Item : Loggable'Class) is
         Marker : constant String := (if Item.Severity >= 3 then "!! " else "   ");
      begin
         Put_Line (Marker & Item.Log_Line);
      end Log;
   end Logging;

   package Events is
      use Logging;

      type Event is tagged record
         Minute : Natural;
      end record;
      function Time_Stamp (E : Event) return String is
        ("minute" & E.Minute'Image & ":");

      --  Extends Event AND implements Loggable.
      type Door_Opened is new Event and Loggable with record
         Door : Positive;
      end record;
      overriding function Log_Line (D : Door_Opened) return String is
        (D.Time_Stamp & " door" & D.Door'Image & " opened");
      overriding function Severity (D : Door_Opened) return Natural is (1);

      type Overheat is new Event and Loggable with record
         Celsius : Integer;
      end record;
      overriding function Log_Line (O : Overheat) return String is
        (O.Time_Stamp & " motor at" & O.Celsius'Image & " C");
      overriding function Severity (O : Overheat) return Natural is
        (if O.Celsius > 90 then 3 else 2);
   end Events;

   use Events;
begin
   Logging.Log (Door_Opened'(Minute => 4, Door => 2));
   Logging.Log (Overheat'(Minute => 9, Celsius => 85));
   Logging.Log (Overheat'(Minute => 12, Celsius => 97));
end Main;
```

It prints:

```text
   minute 4: door 2 opened
   minute 9: motor at 85 C
!! minute 12: motor at 97 C
```

`Log` takes `Loggable'Class`, so it accepts any type that implements the interface, today's or tomorrow's. Inside it, `Item.Severity` and `Item.Log_Line` dispatch. Each event's `Log_Line` calls `Time_Stamp`, which it inherits from `Event`. The package `Logging` never mentions `Events`: dependencies point from the specific to the general, which is how large systems stay maintainable.

### Controlled types: cleaning up automatically

Many objects hold something that must be released: a file, a lock, a hardware channel, a valve that must be closed. Ada's answer is the **controlled type**. Extend `Ada.Finalization.Controlled` (or `Limited_Controlled`, for objects that must not be copied) and override `Initialize`, called when an object is created, `Finalize`, called when it ceases to exist, and, for non-limited types, `Adjust`, called after a copy. C++ programmers know this pattern as RAII.

```ada check
pragma Ada_2022;
with Ada.Text_IO; use Ada.Text_IO;
with Ada.Finalization;

procedure Main is

   package Valves is
      --  A limited controlled type: Initialize and Finalize run automatically.
      type Valve (Id : Positive) is new Ada.Finalization.Limited_Controlled
        with null record;
      overriding procedure Initialize (V : in out Valve);
      overriding procedure Finalize (V : in out Valve);
   end Valves;

   package body Valves is
      procedure Initialize (V : in out Valve) is
      begin
         Put_Line ("valve" & V.Id'Image & " opened");
      end Initialize;

      procedure Finalize (V : in out Valve) is
      begin
         Put_Line ("valve" & V.Id'Image & " closed");
      end Finalize;
   end Valves;

   procedure Fill_Tank (Fail : Boolean) is
      Inlet : Valves.Valve (Id => 1);
   begin
      Put_Line ("filling...");
      if Fail then
         raise Program_Error with "level sensor fault";
      end if;
      Put_Line ("tank full");
   end Fill_Tank;
begin
   Fill_Tank (Fail => False);
   Fill_Tank (Fail => True);
exception
   when Program_Error =>
      Put_Line ("handled the fault in Main");
end Main;
```

It prints:

```text
valve 1 opened
filling...
tank full
valve 1 closed
valve 1 opened
filling...
valve 1 closed
handled the fault in Main
```

In the second call an exception leaves `Fill_Tank` early, and the valve is still closed, before the handler in `Main` runs. No `finally` block is needed and none can be forgotten. `Valve` has a discriminant, `Id`, which must be given when an object is declared; `with null record` means the extension adds no components. In GNAT, the standard containers and `Unbounded_String` are built on controlled types, which is how they free their memory without a garbage collector.

<Narrator who="margaret">

Declare a second valve, `Outlet : Valves.Valve (Id => 2);`, after `Inlet` and run it again. Each call now prints `valve 1 opened`, `valve 2 opened`, and at the end `valve 2 closed` before `valve 1 closed`, with or without the exception: objects are finalized in the reverse order of their creation, as C++ destructors are, so something acquired later, which may depend on what came before, is released first.

</Narrator>

<Section id="human" kind="human" title="How Ada programmers use object orientation">

Ada programmers tend to use object orientation less than Java or C# programmers do, and more deliberately. A few habits are common in professional code:

- **Closed sets get records and `case`; open sets get tagged types.** If the kinds are known and few, a discriminated record with `case` statements is simpler, faster and fully checked by the compiler. Tagged types earn their place when new kinds are expected, or come from other teams.
- **Shallow hierarchies, interfaces for capabilities.** One root type with a level or two of extensions, plus interfaces for cross-cutting abilities such as logging or serialisation, is typical. Deep hierarchies are hard to reason about in any language.
- **One package per type, or per small family.** The package boundary gives each type its own private part, so extensions declared in other packages cannot touch the parent's private components unless they are child packages.
- **Few pointers.** Indefinite containers and class-wide parameters cover most needs without access types. When pointers are necessary (Ada calls them **access types**), they are usually hidden inside a package, and SPARK now supports an ownership model for them similar to Rust's.
- **Analysable dispatching.** In safety-critical code, certification guidance such as DO-332, the object-oriented supplement to the avionics standard DO-178C, asks for evidence that dispatching calls are safe; Ada's explicit split between static and dispatching calls makes that evidence easier to produce.

<Narrator who="chloe">

The first habit is an instance of what Philip Wadler named the *expression problem*. With a variant record, adding an operation is easy (one more `case`) but adding a kind touches every `case`; with tagged types, adding a kind is easy (one more extension) but adding an operation touches every type. No design makes both free, so choose by the direction in which you expect the program to grow.

</Narrator>

<Section id="misconceptions" kind="misconceptions" title="Common misunderstandings">

<Misconception>

**"Ada has no object orientation, or only a bolted-on one."** Ada 95 added tagged types, dispatching and abstract types, and Ada 2005 added interfaces and prefixed notation. Ada's OO is complete; it simply reuses packages for encapsulation rather than introducing a `class` construct.

</Misconception>

<Misconception>

**"Every call to a primitive operation dispatches."** Only calls whose controlling argument is class-wide dispatch. `Describe (C)` with `C : Coach` is bound at compile time to `Coach`'s version.

</Misconception>

<Misconception>

**"Ada supports multiple inheritance."** A type has exactly one parent and inherits components only from it. It may implement several **interfaces**, which carry operations but no data, so the diamond problems of full multiple inheritance do not arise.

</Misconception>

<Misconception>

**"Without `finally`, cleanup after an exception has to be written by hand in every handler."** Controlled types run `Finalize` whenever an object goes out of scope, normally or because of an exception. Put the cleanup in the type once and it cannot be forgotten.

</Misconception>
